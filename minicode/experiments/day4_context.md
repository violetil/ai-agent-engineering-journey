## 发现

### 1. 治理没有发生，原因有三个，都和模型无关

**过期标记有一个字母级的 bug。** `context.py` 第 78 行：

```python
mut = last_mutation.get("path") if path else None
```

`"path"` 带引号，查的是字面量键 `"path"`，永远是 `None`。应该是变量 `path`。六次运行里至少 `160020` 那次（读 → 改 → 再读 → 再改）满足过期条件，没有标上。

**去重没有可去的东西。** 六次运行里没有任何一次出现完全相同的 `(工具, 参数)`。模型读第二次时用了 `offset=40, limit=25`，参数不同，不算重复。

**归档的窗口比整个对话还大。** `KEEP_RECENT=20`，六次运行最多 21 条消息，`messages[1:cutoff]` 在五次里是空切片，第六次只覆盖 1 条 user 消息。`token_budget=32000` 也从没被碰到（最大单步 5,054）。

Phase 0 第一轮实验的结论原文是「两个预算跑出一模一样的 token 数，不是治理没用，是实验没测到东西」。这次是同一件事：六次运行的 token 曲线形状完全一样，分组不可区分，因为没有任何机制改变过 messages。

### 2. 不改写历史时，缓存命中 84–90%

这是这轮实验真正拿到的东西：**基线**。每一步只有新追加的那一截是未命中，平均每次运行只有 2,625 个未命中 token。按 DeepSeek 命中价约为未命中的十分之一算，`155854` 的有效成本约 2,506 + 17,792 × 0.1 ≈ 4,285 个「未命中等价 token」，是名义 20,298 的 21%。

这给第四讲那个悬而未决的问题划了一条线：任何改写历史的治理（归档、去重、过期标记）都会让改写点之后的前缀失效一次。改写是一次性的（标记之后内容稳定，下一步又能命中），所以代价是「改写点之后的 token 数 × 0.9」，付一次。省下的则是之后每一步都少发那些 token。粗算：改写点之后还剩 k 步，被压掉 d 个 token，收益 d × k × 0.1（命中价）减去一次性 (改写点之后的总 token) × 0.9。治理只在「压掉得多、后面步数多」时划算。这个公式下一轮实验要拿数字验。

### 3. 策略层把每一次语法检查都拦下来确认

`commands.log` 里六次 `python -c "import ast; ast.parse(...)"` 全部是 `confirm`，原因是「无法解析命令片段：`python -c "import ast`」。`_SEPARATORS` 在引号内部也按 `;` 切，切出来的片段引号不配对，`shlex` 抛 `ValueError`，归入 confirm。`cd lib && python -c "..."` 那条同理。

后果：白名单里的 `python` 命令因为参数里有分号就失效了，每次运行都要人按一次 y。第一次等了 40 秒（15:58:11 → 15:58:51），之后几次 3–10 秒。六次运行的墙上时间因此都混入了人的反应时间，这轮没有记时间列。

### 4. 模型的行为：稳定、会自纠、会超额验证

六次的编辑策略一致：`import` 一处、签名一处、循环开头一处，`old_string` 全部带了足够的上下文，`edit_file` 零拒绝。四次先 `list_dir` + `grep` 侦察再读，两次直接读。

`160020` 第 2 步写了 `return LoopResult(last_answer(messages), ...)`，`last_answer` 不存在。第 3 步的 thought：「第三处改动我引用了不存在的 `last_answer(messages)`。这是我自行引入的辅助函数，并非用户要求……我先读回确认。」然后读了 40–65 行，改成 `""`。没有跑任何东西，是重读自己的 diff 时发现的。

`160122` 在任务要求的 `ast.parse` 之外，自己写了 `cd lib && python -c "... e.set(); r = L.run_loop([...], cancel_event=e); print(r.stop_reason, ...)"`，拿到 `cancelled '' []`。这是六次里唯一一次行为级验证，其他五次只验了语法。

### 5. `main.py` 的「命中」列算错了

`cache = sum(t.cache_hit_tokens for t in result.steps)` 没有按 step index 去重。同一步多个 `tool_calls` 共享一次 API 调用的 usage，会被加多次。`155854` 打印的命中是 25,728，总输入才 20,298。正确值 17,792。这和 Phase 0 `print_summary` 里 `per_step` 去重是同一个问题，当时只对 prompt/completion 做了，新字段漏了。

## 结论

1. 这一轮没有测到治理。三个机制一个没触发：一个 bug、一个任务太短、一个窗口太大。v0.3 没有验收。
2. 拿到了缓存基线：不动历史时 88% 命中，未命中只有追加的部分。这是下一轮对照组的参照。
3. 策略层的分段逻辑有缺陷，任何带 `;` 的引号内参数都会把白名单命令降级成确认。
4. 任务本身（Phase 0 遗留债务第一条）六次都做对了，`scratch/lib/agent/loop.py` 的 diff 可以直接搬回 `week4_agent/agent/loop.py`。

## 治理组 `105536` 为什么没做完

第 13 步 `edit_file` 给 `loop.py` 加了 `import threading`。进入第 14 步之前，`compact` 把第 2 步读到的 `loop.py` 全文（消息下标 7）替换成 `[内容已过期：lib/agent/loop.py 在此之后被 edit_file 修改过……]`。模型正准备改签名，它上一步还看得见的文件内容没了，于是凭记忆写了 `old_string=') -> str:'`——实际是 `) -> LoopResult:`——被 `count == 0` 拒绝。接下来 grep、读、改签名、读、改循环体、读……第 20 步耗尽，强制收尾的回答自己写着「loop.py 的语法检查尚未执行」。

对照组三次都是同一份读取撑到底：`110539` 第 13、14、15 步对 `loop.py` 连续三次 `edit_file`，中间没有重读；`110923` 第 11–13 步同样。模型靠 `edit_file` 返回的 diff 知道文件变成了什么样，不需要重读。六次里没有一次「用过期内容构造 old_string 被拒」——对照组唯一一次被拒（`110923` 第 5 步）是因为 `tools.py` 第 233、241 行是只含两个空格的空行，`read_file` 输出里看不出来，模型用 `repr` 打印后才发现。

第四讲给过期标记的理由是「改过之后的旧读取是错的，模型会凭它构造错误的 old_string」。数据说的是反面：**模型靠 diff 维护自己的文件视图，旧读取加上 diff 就是当前状态；把旧读取拿走才会让它凭记忆出错。** 过期标记在 `edit_file` 之后触发，是把模型的工作记忆抽掉了。

## 另外几件事

`105949` 第 12 步的测试命令里写了 `../../notes.txt`，被 `_escapes_workspace` 升级成 confirm——day3 「未覆盖」里的这一项这次在模型手上触发了。`110923` 有三次 confirm 全是 `cd lib`、`cd ..`，`cd` 不在白名单。策略层的 `;` 修好之后，六次运行里 `python -c "...; ..."` 全部 allow。

模型自己加的验证远超任务要求：六次里五次写了真实的 `run_loop(cancel_event=ev)` 调用拿到 `cancelled`，四次用 `python -c` 实际调用新的 `read_file` 测分页、续读、越界三种情况。

还有一个测试没抓到的 bug：`mark_stale_and_dedupe` 的去重分支用 `startswith("[")` 判断「已经改写过」，而 `read_file` 的正常输出以 `[path 第 a-b 行` 开头，`run_shell` 以 `[exit code` 开头——这两种工具的结果永远不会被去重。`smoke_context` 没抓到是因为测试里的假内容是「第一次读到的内容」，不以 `[` 开头。测试数据长得不像真数据，测试就不可信。

## 结论

1. 过期标记作为「正确性机制」的前提不成立：模型不会误用改过的旧读取。它作为「省钱机制」是负收益：名义输入省 7.5%，缓存失效让有效成本涨 36%，还多花步数、多一次失败。
2. 不超预算时任何改写历史的操作都是亏的。去掉 d 个 token 每步省 d × 0.1（它们本来是命中），而改写一次让后缀按 0.9 的差价重付一次。十几步的任务永远赚不回来。
3. 归档和摘要这次仍然没有被测到，因为治理组的上下文一直在 12,000 以下。它们的实验留到 Phase 3 的评测基础设施里做，用真实仓库的长任务。
4. `read_file` 改按行分页这件事六次都做对了，其中一次的实现保留在 `scratch/` 里。

## v0.3 改法

- `edit_file` 不再触发过期；只有 `write_file` 整体覆盖才触发（旧读取确实全错了）。
- 「取代」规则替代「过期」：同一文件更晚、范围覆盖更广的一次读取，取代更早的读取。读取的范围从页眉 `第 a-b 行` 解析。
- 过期（正确性）每步跑；去重和取代（省钱）只在超预算时跑，和归档同一道门。
- 「已改写」的判断改为匹配五种标记前缀，不再用 `[`。
- 测试数据用真实格式的页眉和内容。

# 第三轮：v0.3 改法上线，预算 9000，门没开

## 估算为什么系统性偏低

`count_tokens` 只数 messages。每次请求还带 `tools=` 参数——六个工具的 JSON schema，cl100k 1,529 个 token——它算在 `prompt_tokens` 里，不在 messages 里。逐步对照：

| step | 估算（只数 messages） | 估算 + schema | 真实 prompt |
| ---- | --------------------- | ------------- | ----------- |
| 1    | 903                   | 2,432         | 2,100       |
| 5    | 5,204                 | 6,733         | 6,310       |
| 10   | 6,587                 | 8,116         | 7,823       |
| 14   | 7,635                 | **9,164**     | 9,111       |
| 16   | 7,909                 | 9,438         | 9,443       |

加上 schema 之后，估算和真实值相差 <5%，到后期几乎重合（前期 cl100k 对中文 description 略高估）。第二轮「cl100k ≈ 真实」的结论是对的，但当时拿最终 messages 比最后一步的 prompt，两个方向的误差正好抵消，没发现少了这一块。

## 如果门开了会发生什么（回放）

把这份 trace 的真实历史逐步喂给修正后的 `compact(budget=9000)`：第 14 步越线（9,164 > 9,000），`dedupe_reads` 找不到可省的（没有重复读取），`archive_old_tool_results` 把保留窗口外的 12 条 tool 结果归档，估算降到 7,002。第 15、16 步各再归档 1–2 条。代价：第 14 步改写了从下标 3 开始的历史，第 15 步的未命中会从两百多跳到约 7,000（整个前缀重算一次）。这就是第二轮结论 2 说的那笔账，这次会以归档的形式出现。

## 修法

`context.py` 加 `context_size(messages) = count_tokens(messages) + schema token 数`，`compact` 里四处比较预算都换成它。schema 在注册表加载后不变，算一次缓存。

另：`experiments/smoke_context.py` 里 `compact` 的测试会往 `logs/agent.log` 写 `上下文：去重/取代 2 条`（10:55:15 那行），看 log 时别把它当运行痕迹。

## 每次改写的即时代价

| `112940` 第 15 步        | 8,843             | 6,852               | **4,676**    | ~200       |
| `113816` 第 6 步         | 7,879             | 5,845               | **3,669**    | ~200       |

每次归档省下约 2,000 token 的名义输入，这 2,000 本来是命中（0.1 价），每步省 200 有效 token；而改写那一步付了 3,500–4,700 的全价。要靠后面省的把它赚回来需要 18–24 步，任务只有 13–20 步。和第二轮结论 2 一致，这次是归档形式的实测。

## 归档拿走的恰好是下一步要用的

`113816` 第 6 步前归档了 `loop.py 1-88` 的读取，模型紧接着在第 6 步**重新读了一遍 `loop.py` 全文**（它刚改完 tools.py，下一件事就是改 loop.py）。`112940` 第 15 步前同样归档了 `loop.py` 的读取，模型第 15 步重读 `loop.py` 44–68 行再继续改。两次里两次，归档窗口按「最近 8 条消息」切，不知道任务还有哪个文件没动。重读本身又是一笔未命中（1,175 / 367）加一步。

这是归档策略的结构性问题：按时间窗口归档假设「旧的就是不需要的」，而编码任务里「读过但还没改」的文件恰恰是接下来最需要的。正确的策略需要任务层面的信息（哪些文件在任务里被提到、哪些还没被 edit 过），Phase 3 再做。

## 摘要第一次发生（`113307`）

第 4 步 `git diff` 输出很大，加上保留窗口里两个全文读取，归档 1 条（list_dir）后仍超预算，于是摘要。切点 `cut = 12 - 8 = 4`，被摘要的只有 `messages[1:4]`：用户任务 + 一次 list_dir。摘要 443 字，任务约束一字不漏地保留了（offset 从 1 起、limit 默认 200、右对齐 6 位、cancel_event 签名、ast.parse 命令、git diff --stat），还如实写了「两处修改均未开始」。模型之后仅凭摘要就正确验证完成。

代价：多一次模型调用，第 5 步未命中 6,590（摘要在下标 1，之后全部失效），而省下的名义 token 几乎为零（用户消息换成了同样长的摘要）。这就是「预算低于地板」的实际样子——没有触发 warning，因为摘要后刚好压到了 9000 以下，但省钱为负。

## `112940` 为什么 20 步

不是治理的锅。第 3 步 `edit_file` 替换的 `old_string` 包含了 `register(Tool(...))` 段落而 `new_string` 没有，等于删掉了注册；模型第 4 步 grep + 读尾部发现，第 5 步补回。第 6–11 步在折腾测试命令的导入路径（`sys.path.insert(0,'.')` 还是 `'lib'`、`PKG_ROOT` 指向哪）。这两处花了 8 步。治理导致的只有第 15 步那次重读。

## 第四讲最终结论

1. v0.3 的四个机制都在真实运行里发生过了：过期（第二轮）、归档（第四轮三次）、摘要（第四轮一次）、去重/取代（从未——按行分页之后模型不会重复读同一范围，这个机制对这类任务是空的）。
2. 在 DeepSeek 这种前缀缓存 + 命中 0.1 价的计费下，**不超过模型窗口时，任何改写历史的操作都是负收益**。省钱的正确手段是让工具结果一开始就小（按行分页、grep 只返回匹配行、shell 截 head/tail），不是事后压缩。
3. 改写历史的唯一正当理由是正确性（`write_file` 之后的旧读取）和窗口上限（真的塞不下）。预算应设在接近模型窗口的位置，而不是用来「省钱」。
4. 模型维护文件视图的方式是「旧读取 + diff」；拿走任何一个都会引发重读或凭记忆出错。
5. 测试数据必须长得像真数据（`startswith("[")` bug）；估算必须对照真实值校准（schema 那 1,500 token）。

v0.3 保留现状，默认 `--token-budget` 改为 32000（接近实用窗口，正常任务不触发），`--no-governance` 保留做对照。第四讲到此收口。
