# 建路线图

路线图不是课程大纲，是一条**以主线项目为骨架、以硬验收为关卡**的路径。学习者在每个阶段末尾都要拿得出一个可运行的东西和一份有数字的记录。

## 1. 盘点现状（先读仓库，再下结论）

打开学习者的仓库、笔记、已有作品，逐个目录看，不要只看 README。产出一张能力表：

| 能力域 | 现状（写证据：哪个文件、哪份记录） | 补齐阶段 | 状态 |
|---|---|---|---|
| … | 「扎实（week1 有实验与报告）」/「只有讲义，代码未写」/「空白」 | 已具备 / Phase N | 绿 / 黄 / 红 |

规则：

- 「现状」一栏必须引用证据。写「扎实」要能指出文件；写「空白」要确认搜过。
- 把学习者的**差异化优势**单独点出来（例如转行者里少见的后端工程底子）。路线图要让优势成为主线项目的一部分，而不是从零开始。
- 找出**半成品**：读过讲义但没写代码、写了代码但没做实验、做了实验但没写记录。半成品优先收尾，这通常就是 Phase 0。

## 2. 确认目标与约束

从用户的话里提炼三件事，写进 ROADMAP 开头，后面每个决策都要能回溯到它们：

- **终点**：找到某类岗位 / 熟练掌握某技术栈 / 交付某个产品。多个目标时排序。
- **方式偏好**：用户是否明确说过「以项目为目标」「先手写再用框架」「你给代码我自己写」。这些是铁律的来源，原文记下。
- **约束**：时间、设备、已有技术栈、不愿意碰的东西。

## 3. 选主线项目

一个项目贯穿全程，每阶段给它加一层。选择标准（全部满足才选）：

1. 天然覆盖该领域的核心考点，而不是只覆盖一两个。
2. 验收标准客观：测试过没过、bug 修没修、指标到没到，不靠感觉。
3. 能直接复用学习者已有的代码和能力（第 1 节的优势）。
4. 是目标岗位或目标产品的「最小内核」，做完能撑起一次面试或一次演示。
5. 有公开的成熟参照物（开源项目、知名产品），学习者卡住时有地方看。

在 ROADMAP 里用一段话写清楚**为什么选它、为什么不选另外两个候选**。

## 4. 分阶段

一般 5–6 个阶段，顺序由依赖决定，不由难度决定。每个阶段写五样东西：

```markdown
### Phase N · 标题（一句话说这阶段加了哪一层）
- 周期：第 a–b 周（可弹性，顺序不跳）
- 目标：一句话。为什么这阶段非做不可，它解决上一阶段暴露的什么问题。
- 做什么：3–5 条可交付的增量，每条是名词短语 + 动词（「v0.2 安全层：路径校验 + 危险命令确认」），不是知识点列表。
- 硬验收：一句可以判定真假的话。「一条 curl 命令带 JWT 调 /agent/run，SSE 实时看到每一步」可以；「掌握 SSE」不可以。
- 预计讲数：每讲对应一个可交付增量。
```

阶段设计的经验规则：

- **Phase 0 = 收尾半成品。** 没有收尾的东西在面试里一文不值，而且后续阶段要复用它。
- **把「评测 / 可靠性」单独设成一个阶段。** 会做的人多，会科学评测的人少，这一阶段拉开差距。
- **框架、生态、热门关键词放在手写内核之后。** 先知道每个抽象在解决什么问题，再学框架。
- **最后一个阶段是产品化与作品集。** 陌生人打开仓库五分钟内能看懂、看到 demo、跑起来。
- 不写日历日期级别的计划；周数只是量级提示。

## 5. 里程碑、并行线、执行原则

- **里程碑**：8–10 条，每条是一个可以打勾的事实（「MiniCode 独立修复陌生仓库的真实 bug」）。第一条是 Phase 0 的收尾。
- **并行线**：贯穿全程的事。求职目标下是「每阶段一篇深度博客 + 收集 JD + 面试考点对照表」；研究目标下是「每阶段一次复现 + 读 N 篇论文」。做成表：考点 / 要能讲清楚的内容 / 对应阶段。
- **执行原则**：4 条左右，从用户的方式偏好推出来。原始会话的四条可直接复用：
  1. 每周产出可运行的增量，宁可砍范围不砍闭环。
  2. 每阶段的验收是硬门槛，没过不进下一阶段；周期可以拉长，顺序不要跳。
  3. 所有对比实验留下数字，它们是博客和面试里最有说服力的素材。
  4. 框架放到手写内核之后。

## 6. 产出文件

### `learning/ROADMAP.md`

章节顺序：标题与一句话总述 → 目标与约束 → 现状盘点表 → 为什么选这个主线项目 → 各阶段 → 里程碑 → 并行线 → 执行原则 → 页脚（依据、制定日期、最后更新日期）。

可选：同时生成一个 canvas（有 `cursor/canvas` 时），结构同上，阶段用可折叠卡片，里程碑用可点击的 todo 列表。canvas 是展示层，`ROADMAP.md` 是真相来源。

### `learning/PROGRESS.md`

```markdown
# 进度

- 当前阶段：Phase 0
- 当前讲次：未开始
- next_action: lecture          # lecture | review | wrapup
- 最后更新：YYYY-MM-DD

## 阶段与讲次

| 阶段 | 讲 | 主题 | 状态 | 讲义 | 记录 |
|---|---|---|---|---|---|
| P0 | 1 | 拆包 + 上下文治理 | planned | | |
<!-- 状态：planned → lectured → submitted → passed / blocked -->

## 待修（阻塞下一讲）

- [ ] （验收时发现、必须在下一讲之前修好的项，附出处记录）

## 债务（不阻塞，阶段末汇总进博客「还不能上生产」）

- （已知问题 + 修法方向 + 出处）

## 已核实的事实（供后续讲义引用，避免凭记忆）

- 治理地板约 8–9k token（records/p0-l01）
```

四个子技能都读写它。`next_action` 决定下一回合走哪个技能。

## 7. 回复中怎么呈现

- 先给一段总述：主线项目是什么、为什么、总共几个阶段、第一步做什么。
- 再给现状盘点表与阶段列表（或 canvas 链接）。
- 最后一句明确下一步：「准备好了说『指导我做完 Phase 0』」。
- 不要在同一回合开始讲第一讲。

## 发送前自检

- 现状表每一行的「现状」都有文件级证据？
- 主线项目的五条选择标准逐一满足并写明？
- 每个阶段都有可判真假的硬验收？
- 用户原话里的方式偏好被原文记进 ROADMAP 的「约束」节？
- `PROGRESS.md` 已创建且 `next_action: lecture`？
