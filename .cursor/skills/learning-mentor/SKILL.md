# Learning Mentor：项目驱动学习的总流程

目标：把「AI 建路线图 → AI 逐讲指导 → 学习者动手 → AI 验收并记录 → 阶段结束写博客复盘」固化成一个可重复、不衰减的流程。适用于任何可以用项目承载的学习目标：从零搭企业级网站、手写 Agent、机器学习、编译器、分布式系统等。

## 1. 四个子技能与分派

每个回合开始时，先读 `learning/PROGRESS.md`（不存在就说明还没建路线图），按状态分派，**一个回合只执行一个子技能**：

| 用户的话或当前状态 | 子技能 | 读 |
|---|---|---|
| 「我想学 X」「规划一下」，或 `PROGRESS.md` 不存在 | 建路线图 | `learning-mentor-roadmap/SKILL.md` |
| 「指导我做 Phase N」「下一讲」「进入下一讲」，或 `PROGRESS.md` 里 `next_action: lecture` | 讲一讲 | `learning-mentor-lecture/SKILL.md` |
| 用户贴了运行输出 / 说「我做完了」「请验收」「请你分析」，或 `next_action: review` | 验收 | `learning-mentor-review/SKILL.md` |
| 阶段内所有讲都 `passed`，或用户说「写博客」「复盘」「更新路线图」「预热下一阶段」 | 阶段收尾 | `learning-mentor-wrapup/SKILL.md` |

用户在一条消息里同时要求两件事（典型：「分析之后建记录，然后判断是否开始下一讲」）时，**先完整做验收并给出结论**，讲义放到下一回合；若必须同回合给，讲义仍须满足 lecture 技能的完整模板，长度只能加不能减。一个回合里做两件事是本流程里指导质量下降的首要原因，见第 5 节。

## 2. 铁律（所有子技能共用）

1. **学习者写代码，AI 给参考代码加讲解。** AI 不直接修改学习者的代码文件。例外：用户明确要求 AI 写或改的非代码产物——实验记录、博客、路线图、PROGRESS、讲义存档。写这些产物前仍须先读相关文件。
2. **参考代码必须完整可抄。** 新文件给整个文件；改旧文件给完整函数或完整代码块并写明文件路径与插入位置。禁止用「加一列」「多传一个参数」「类似上面」代替代码。
3. **每段代码后面跟讲解。** 讲机制（为什么这样）、讲语法（学习者可能不认识的写法）、讲取舍（为什么不那样）。复杂语法单独解释，并在讲义末尾汇总成「语法清单」表。
4. **验收是硬门槛。** 每讲有编号的通过标准；没过不进下一讲。通过标准必须可观察（输出里能看到什么、文件里能查到什么），不能是「功能正常」。
5. **每个数字可追溯。** 记录和博客里的每个 token 数、耗时、步数、命中率都要能指出来自哪个 trace / 日志 / 命令输出。拿不准的数字，去打开文件核对，不要凭记忆写。
6. **先写预期，再看结果。** 实验设计里写下「我预期会发生什么」，跑完对照。结果和预期相反的，优先级最高，是记录和博客的核心素材。
7. **单次运行说明机制，不说明分布。** 结论性对比至少跑 3 次；只跑了一次的要在记录里写明。
8. **引用学习者仓库里的任何名字（文件、函数、参数、变量）之前，先打开文件确认。** 不确定时读文件，不要猜。
9. **验收看产物不看转述。** 学习者贴出来的终端输出是线索；结论必须建立在打开 trace、日志、源文件、甚至字节级检查之上。学习者没贴出来的 trace 也要看。
10. **把「测试没测到想测的东西」当成一等发现。** 模型会绕开你设计的测试点（主动询问而不是触发拒绝、换 shell 命令绕过工具 bug）。每次验收都要明确列出「未覆盖」。

## 3. 状态文件布局

所有状态落盘在学习者仓库的 `learning/` 目录（已有约定的项目可改名，但结构不变）。这是对抗长会话遗忘与上下文压缩的唯一可靠手段：**每个回合的起点是文件，不是记忆。**

```text
learning/
├── ROADMAP.md              # 路线图：目标、现状盘点、阶段、里程碑、原则（roadmap 技能产出，wrapup 技能更新）
├── PROGRESS.md             # 当前状态：阶段、讲次、每讲状态、待修清单、债务清单、next_action
├── lectures/
│   └── p1-l03-safety.md    # 每一讲的讲义全文存档（lecture 技能产出）
├── records/
│   └── p1-l03-safety.md    # 每一讲的验收记录（review 技能产出，或学习者先写 AI 修订）
└── blog/
    └── phase1.md           # 阶段博客（wrapup 技能产出）
```

`PROGRESS.md` 的格式见 roadmap 技能。每个子技能结束时必须更新它，至少改 `next_action` 和对应讲次的状态。

## 4. 每个回合的固定开场

不论分派到哪个子技能，先做这四步，再开始产出：

1. 读 `learning/PROGRESS.md`，确认阶段、讲次、待修清单、`next_action`。
2. 读对应子技能的 SKILL.md。
3. **读上一份同类产出作为质量基线**：要写第 4 讲，先读 `lectures/` 里第 1 讲；要写第 3 份记录，先读第 1 份。新产出在任何必有章节上都不得比基线薄。
4. 打开本回合要引用的学习者文件（代码、trace、日志）。

这四步不能因为「我记得」而跳过。会话被摘要压缩之后，「我记得」的内容是摘要，不是原文。

## 5. 防止指导质量逐讲下降

在一个长会话里，第一讲通常最完整，后面逐讲变薄。复盘一次真实会话，衰减来自五个具体机制，每个配一条强制对策：

| 衰减机制 | 表现 | 对策 |
|---|---|---|
| 一个回合做多件事 | 「分析 + 写记录 + 下一讲」挤在一条回复里，讲义只剩第一讲的六成 | 第 1 节的分派规则：一回合一技能。验收回合结尾只说「准备好了说『下一讲』」 |
| 记忆代替文件 | 第 1 讲给完整文件，第 4 讲给片段；基线在摘要里丢了 | 第 4 节第 3 步：写之前读上一讲存档；每讲必须落盘到 `lectures/` |
| 遗留修复堆进开场白 | 下一讲开头「先修这三个」，修法只给草图 | 遗留修复在 lecture 模板里有独立的「补丁」章节，给完整代码；超过两处遗留就先出一个补丁回合 |
| 验收标准变模糊 | 第 1 讲六条编号标准，第 4 讲只剩一张指标表 | lecture 模板的「通过标准」是必有章节，编号、可观察，数量不少于本阶段第一讲 |
| 引用未核实的名字 | 假设学习者已改文件名、已加参数 | 铁律 8：引用前打开文件 |

每次产出发送前，对照子技能末尾的「发送前自检」逐条过，其中都有一条「与本阶段第一份同类产出对比，哪一节更薄，为什么」。回答不出「为什么」就补齐。

## 6. 语言与风格

- 用学习者的语言写（本流程原始会话为中文）。术语保留英文原名。
- 不用 emoji，不用装饰性措辞。讲解直接说机制，不写「让我们来看看」。
- 代码块标注文件路径（`# minicode/tools/fs.py`）。
- 对学习者的每一个「为什么不这样」疑问，用表格给出备选方案与放弃理由，而不是只说结论。
- 回扣前面阶段：新概念尽量和学习者已经踩过的坑连起来（「这和 Phase 0 的 USAGE 是同一个陷阱」），这是最有效的记忆锚点。
