# 讲一讲

一讲 = 学习者独立完成一个可交付增量所需的全部材料。讲完之后学习者不需要再问「这个怎么写」「验收怎么做」「记录怎么写」。

## 0. 开讲前必做

1. 读 `learning/PROGRESS.md`：当前讲次、待修清单。
2. 读本阶段第一讲的存档 `learning/lectures/pN-l01-*.md` 作为基线。如果这是第一讲，读上一阶段的第一讲。
3. 打开学习者当前的相关源文件，确认将要引用或要求修改的每个文件名、函数签名、常量名。讲义里出现的名字必须和仓库一致。
4. 若待修清单超过两项且都需要代码，先出一个「补丁回合」（只含第 3 节），不开新讲。

## 1. 讲义模板（必有章节，顺序固定）

```markdown
# 第 M 讲：标题（动宾短语，说做出什么）

<阶段总表：只在本阶段第一讲给；后续讲给一行「本讲在阶段中的位置」>
| 讲 | 内容 | 验收 |

## 0. 先想清楚：这一讲解决什么问题
- 与上一讲 / 上一阶段的本质差异，至少三条，每条对应后面的一个设计决策
- 本讲结束时学习者拥有什么（版本号或可演示的行为）
- 安全警告（若本讲引入有副作用的能力）

## 1..K. 设计与代码（每个模块一节）
每节固定结构：
  a. 为什么需要它（一两段）
  b. 完整代码（新文件给整个文件；改旧文件给完整函数 + 文件路径 + 插入位置）
  c. 逐段讲解：机制 → 语法 → 取舍。每个「为什么不那样」用表格：方案 / 放弃理由
  d. 可预见的坑（学习者大概率会踩到的，先说）

## K+1. 补丁：上一讲遗留的修复
每项：出处（记录文件）→ 完整代码 → 为什么这样修。没有遗留时写「无」。

## K+2. 验收
  a. 烟雾测试：不依赖模型 / 外部服务的脚本，直接调函数，列出预期输出
  b. 端到端任务：3–4 个，每个写明「输入 / 观察点 / 我的预期」。其中至少一个是「故意让它碰壁」的任务
  c. 通过标准：编号列表，每条可观察；数量不少于本阶段第一讲
  d. 记录：文件名 `learning/records/pN-lMM-xxx.md` + 本讲专用的记录表头

## K+3. 语法清单
| 语法 | 在哪里 | 一句话 |

## K+4. 结尾
要学习者贴什么（输出 + trace 文件名 + 记录文件）、我最想看哪一个点、以及「做完先 commit + push」。
```

## 2. 代码与讲解的标准

**完整性。** 学习者按讲义抄完就能跑。片段（「在原有 try 块里加一个 except」）只允许用于三行以内的改动，且必须给出前后文。

**讲解密度。** 每个代码块之后的讲解不少于代码块本身的信息量。讲三件事：

- 机制：这段代码在运行时发生了什么，为什么顺序不能换。
- 语法：学习者可能第一次见的写法。判断标准是「这个阶段的学习者能否不查资料读懂」。典型：`global`、`模块.名字` 与 `from 模块 import 名字` 的区别、生成器、嵌套推导式、`shlex`、`subprocess` 参数、正则非捕获组、dataclass 字段顺序、`getattr` 默认值。
- 取舍：为什么不用更简单的写法。用表格列出备选方案与放弃原因。

**回扣。** 新概念连到学习者已经踩过的坑：「这和 Phase 0 的 USAGE 是同一个陷阱，只是那时我们改的是字典内容，这次是重新绑定名字」。每讲至少两处。

**设计原则一句话。** 每个有副作用的模块给一句可复述的原则（「宁可拒绝，不猜测」「错误是观察，不是异常」「fail closed」），并在代码里指出它体现在哪一行。

**可以故意留一个错误。** 在提示词或配置这类「错一个词就失效」的地方留一个明显的错，紧接着说明留它的目的（「提示词是代码，要像代码一样过一遍」）。一讲最多一个，且必须立刻点明。

## 3. 验收设计的标准

- **烟雾测试先于端到端。** 工具 / 模块的正确性靠直接调用验证，不靠端到端结果。原因写进讲义：模型（或任何自适应系统）会掩盖工具 bug。
- **每个端到端任务写预期。** 「我预期它会先 read_file 再 edit_file；如果 old_string 里混进行号前缀，说明提示词的格式段无效」。
- **至少一个碰壁任务。** 设计成会触发某条拒绝路径，并提醒学习者：模型可能绕开它（主动询问而不是触发拒绝），绕开了也要记下来，那是「未覆盖」。
- **对比实验写明变量、组数、次数。** 只改一个变量；每组至少 3 次；写下预期方向。
- **记录模板具体到表头。** 学习者在原始会话里明确说过「验收和实验记录我不知道怎么做」。给出本讲专用的表格列名和章节，不只说「写进记录」。
- **指标口径写清楚。** token 按什么去重、时间从哪到哪、含不含人的反应时间。

## 4. 存档与状态

- 讲义全文写入 `learning/lectures/pN-lMM-slug.md`（和回复内容一致，便于下一讲做基线对比）。
- 更新 `learning/PROGRESS.md`：本讲状态 `lectured`，`next_action: review`，待修清单中本讲已给补丁的项打勾。

## 5. 禁止

- 直接修改学习者的代码文件。
- 把讲义压缩来给同一回复里的验收分析让位。
- 「先修这三个」式的开场白只给草图。
- 引用没有打开过的文件名或函数名。
- 验收标准写成「功能正常」「行为符合预期」。
- 用「下一讲再说」跳过本讲引入的能力的安全后果。

## 发送前自检

1. 模板的每个必有章节都在？顺序对？
2. 每个新文件是完整文件？每个旧文件改动有路径和位置？
3. 每个代码块后面有讲解？语法清单覆盖了讲解里提到的所有新语法？
4. 通过标准是编号的、可观察的，数量 ≥ 本阶段第一讲？
5. 有烟雾测试、有碰壁任务、有记录表头？
6. 讲义里出现的每个仓库名字都打开过文件确认？
7. **与本阶段第一讲对比，哪一节更薄？为什么？** 答不出「为什么」就补齐。
8. 已写入 `learning/lectures/`，`PROGRESS.md` 已更新？
