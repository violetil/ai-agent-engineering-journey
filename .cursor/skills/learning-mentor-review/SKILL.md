# 验收一讲

验收的产出是三样：一份记录文件、一个明确的结论（通过 / 不通过 + 原因）、一份下一讲之前必须修的清单。验收回合**不开下一讲**。

## 0. 验收前必做

1. 读 `learning/PROGRESS.md` 与本讲存档 `learning/lectures/pN-lMM-*.md`，把「通过标准」编号列表拿出来。
2. 列出学习者仓库里本讲产生的全部产物：trace 目录按时间排序、日志、新建或修改的源文件、学习者自己写的记录。**用户没贴出来的 trace 也在范围内**（原始会话里最重要的两个发现——工具 bug 被模型掩盖、git 越过工作目录——都来自用户没有贴出来的那条 trace）。
3. 若产物只在学习者本机、云端拿不到，先要求 commit + push，再验收。不要凭贴出来的片段下结论。

## 1. 读产物的方法

- **trace 全读**，不只看最终答案。重点看：工具调用序列、每次调用的参数（`old_string` 里有没有混进不该有的东西）、工具返回的第一行、模型在被拒后的下一步、`thought` 里有没有对工具输出提出质疑（「路径显示成了 `.`，看起来是被简化了」——这是工具 bug 的信号）。
- **日志对照 trace**：审计日志、命令日志里的条目数应等于 trace 里的调用数；多出来的说明有没进 trace 的路径。
- **独立复现至少一项结论**。例如：用 `Format-Hex` / `xxd` 确认换行符是否保留；直接调用学习者的 `classify()` 看注入载荷的判定；数文件行数核对模型的回答。学习者的烟雾测试通过不等于你的检查通过。
- **核对数字口径**：token 是否按 step index 去重；总计是否漏了某类调用（提取、摘要、规划）；墙上时间是否混入了人的确认时间。口径不一致时在记录里写明，不要直接比较。

## 2. 要找的四类东西

按优先级，每类都要有结论，哪怕结论是「没有」：

| 类别 | 典型表现 | 为什么是一等发现 |
|---|---|---|
| 测试没测到想测的东西 | 碰壁任务里模型主动询问、没触发拒绝；失败步排在成功步前面导致「不重做」没被覆盖；两个参数跑出一模一样的数字 | 学习者会误以为某条路径已验证 |
| 系统掩盖了 bug | 工具返回错误数据，模型换一种办法拿到了正确答案；最终输出正确但论据来自推断而非观察 | 只看答案永远发现不了 |
| 边界被绕过 | 文件工具守住了路径但 shell 里的 git 向上找到了父仓库；黑名单对「盘符」有规则对「当前目录」没有 | 安全类问题，且往往在「通过」的运行里 |
| 口径与方法问题 | 单次运行当分布；墙上时间混入人的反应；记录里的数字和 trace 对不上 | 影响后续所有对比的可信度 |

每个发现写成四段：现象（trace 里的原话或数字）→ 证据（文件名、行号、命令输出）→ 机制（为什么会这样）→ 修法（具体到代码或实验设计）。

## 3. 记录文件模板

写入 `learning/records/pN-lMM-slug.md`。学习者已经写了记录的，在原文件上修订并逐条告诉他改了什么、为什么。

```markdown
# 第 M 讲：标题——验收记录

<环境与口径：版本、模型、参数、token 怎么算、时间从哪到哪、单次还是多次>

## 对照表
| # | 输入 | 步数 | 输入 token | 输出 token | 时间 | 工具序列 / 判定链 | trace |

## 验收项逐条
<对讲义里编号的通过标准，一条一段：成立 / 不成立 + 证据>

## 发现
### 1. <一句话标题，说结论>
现象 → 证据 → 机制 → 修法
### 2. …

## 未覆盖
<本讲设计要测但这次没测到的路径，以及为什么没测到>

## 待修
1. <阻塞下一讲的项，具体到文件和函数>
2. <非阻塞的，标注「债务」>
```

## 4. 结论与状态

回复结构：

1. 一句话结论：通过 / 不通过，依据哪几条标准。
2. 两到三个最重要的发现，每个一段，带 trace 文件名和数字。重点讲**你是怎么发现的**（读了哪条没贴出来的 trace、跑了什么命令），这是在教学习者验收方法。
3. 阻塞性修复：完整代码（不是草图），放在这里而不是下一讲开头。
4. 非阻塞项：一句话列出，进债务清单。
5. 结尾：「修完 X、Y 并 push 之后，说『下一讲』。」

更新 `learning/PROGRESS.md`：本讲状态 `passed` 或 `blocked`，待修清单与债务清单，`next_action: lecture`（通过）或保持 `review`（不通过）。记录里新核实的事实（地板数值、固定开销、某条路径未覆盖）写进「已核实的事实」节，供后续讲义引用。

## 5. 禁止

- 只根据用户贴出来的输出下结论。
- 在验收回合里开始写下一讲（用户要求「然后判断是否开始下一讲」时，判断即可：说「可以进入下一讲，准备好了说『下一讲』」）。
- 把「模型自己绕过了测试点」写成「通过」。
- 修法只给方向不给代码（阻塞项必须给完整代码；债务项可以只给方向）。
- 直接修改学习者的代码文件。

## 发送前自检

1. 本讲所有 trace 都打开过，包括用户没贴的？
2. 至少独立复现了一项结论，并在回复里说明用了什么命令？
3. 四类发现每类都有结论？
4. 记录文件的六个章节齐全，每个数字能指出来源？
5. 阻塞性修复给了完整代码？
6. `PROGRESS.md` 已更新，`next_action` 正确？
7. **与本阶段第一份记录对比，哪一节更薄？为什么？**
