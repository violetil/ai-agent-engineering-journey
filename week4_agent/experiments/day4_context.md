# Day 4：上下文治理对照实验

任务（两组相同）：完整读取 `tutorials/agent_loop.md`（17608 字符），然后总结每一节的要点。

文件按 1700 字符分页，完整读取需要 11 次 `read_file`（offset 0, 1700, …, 17000），再加 1 次总结，理论下限 12 步。`max_steps=15`。

对照变量只有 `token_budget`。循环本身的 token 来自 `res.usage`（按 step index 去重后求和），不含摘要器——这次摘要器一次都没跑。

## 治理组实际发生了什么

第 10 步结束后 messages 共 22 条（system + user + 10 组 assistant/tool）。`KEEP_RECENT=6`，于是 `messages[:16]` 里的 7 条 tool 内容被替换成 `[已归档] 原结果开头：…`。消息本身还在，`tool_call_id` 配对完整，所以没有 400。

归档后 tiktoken 估算掉到预算以下，第 2 级摘要的门槛没跨过，所以 `summarize_history` 一次都没调用，`[前情摘要]` 也没出现。`compact` 末尾那条「预算低于地板」的 warning 同样没触发——归档已经把计数压回去了。

## 质量代价

治理组最终答案自己承认：

> 文档第 1–8 节（约前 11900 字符）的内容在读档时被抽离了部分详细输出。

归档只留了每页前 80 字符的 header，事实性正文被扔掉了，而摘要器本该负责把这些事实压进 300 字备忘。因为归档已经让计数「达标」，摘要器根本没有上场。这是分级治理的结构性问题：**便宜的那一级如果单独就能压过预算，更贵但保信息的那一级就永远轮不到。**

对照组没有这个问题，从第 0 节「三句话」写到第 14 节「下一步学什么」，输出也更长（2378 vs 1158 completion tokens）。

## 和 9/2 那次失败实验的对比

`traces/trace_20260902_144114.json`：`max_steps=10`、`token_budget=2500`。预算低于上下文地板，摘要器每步空转 7 次；步数不够读完全文，收尾被 `tool_choice="none"` 卡住，答案泄漏成 DSML 乱码。

这次两处都改对了：步数留到 15，预算抬到地板之上；收尾调用不再传 `tools`。因为两组都自然 `done`，收尾路径这回没被走到。

## 结论

1. 分页 `read_file` + offset 指引有效，两组都精确翻了 11 页，没有同参空转。
2. 第 1 级归档能把 O(n²) 曲线切断，且不破坏协议。
3. 只归档不摘要会丢事实。下一次要把「归档之后如果砍掉了还没写进摘要的工具结果，强制再走一遍摘要」补上，或者让归档保留的不是 header，而是该页的要点。
4. `token_budget` 必须高于 KEEP_RECENT 窗口的地板（这套工具大约 8000–9000 实际 token），否则会回到 9/2 那种步步摘要、负收益的状态。
